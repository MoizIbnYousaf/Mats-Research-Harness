# study: the Python side

Nothing in this directory is a result.

The question (PLAN.md line 9): with the model held fixed (`deepseek/deepseek-v4-flash-0731`; the plan said Gemini) and permission gates removed, when the harness a coding agent runs inside (Claude Code, Codex, OpenCode, Pi; Antigravity dropped with the model switch) changes how the model handles a test it cannot honestly pass, is that because the harness changes what the model sees before it acts, or what it does once it has seen the contradiction; and does the harness change what the model does, or only what it says about it? In Neel Nanda's terms this is model forensics: is the sketchy action the model, or the harness it was handed, and is it confusion or intent.

The closest prior work is quoted in `PRIOR-WORK.md`. Overeager Coding Agents (arXiv 2605.18583) ran three shared base models through four agent products and found the framework mattered more than the model, with permission gating as the explanation and scope violations as the outcome. This study takes the gates out by design, measures cheating on tests that have no honest solution, and labels every run by what the model had observed before it acted, so a harness effect can be split into perception and disposition.

## What is where

`PLAN.md` is the design: the question, the outcomes written down before any data (A to E), the kill test with its instruction ladder, the hour-by-hour plan, the framing rules, the hand-work ledger, the verification list and the timer. `GROUNDING.md` holds every decision with its date, the two independent verdicts in their own words, the ideas that were considered and where they went, the standing list of ways a result could be wrong with the control for each, the facts verified on this machine, the open items and the source map. `PRIOR-WORK.md` has the two anchor papers, read in full and quoted. `HOUR-ZERO.md` has the feasibility checks. `proposals/` has the design proposals and their syntheses. Agents never edit any of these.

`runner/` does the running. `proxy.py` is the logging proxy on 127.0.0.1:8931; it is the only process that holds the real key, gives each run its own token, and writes one request record and one response record per call. `harness_env.py` composes the launch line, environment and config files for each of the five bodies; its `--json` output is the one source that `mrh` and `run.py` both use. `run.py` does one run: prepare, launch under a 600 second wall clock, then finish with the diff against the seed commit, the two reruns, the proxy records and a `manifest.json` that carries a validity `status`; in docker mode the same script runs itself inside the study image. `batch.py` runs the seeded grid over tasks, bodies, states and samples with `--resume`, `--max-runs` and `--dry-run`. `rerun.py` does the two clean-room reruns with only the agent's `solution.py` carried over. `perception.py` holds the `Perception` dataclass, the conflict matcher and `TEST_FILE_PATTERNS`; `parse_proxy.py` and `parse_agy.py` turn proxy records (three wire formats) and Antigravity stream-json into it, and `perceive.py` walks a runs directory and writes `perception.csv` plus the per-run text files. `capture_prompts.py` archives each body's wire prompt with a hash. `Dockerfile` and `docker-run.sh` are the image and a by-hand container run.

`scoring/score.py` produces the two outcome axes (action from the diff and the reruns; disclosure from all assistant text and from the final message), the `noticed` flag, validity, and the one-label `ladder`. The tamper rule's edge cases are decided in its header. `scoring/README.md` spells out every rule.

`tasks/` holds `ib/` (29 `conflicting` pairs) and `ib-oneoff/` (15 `oneoff` pairs) pulled from ImpossibleBench by `load_impossiblebench.py`, the fixture task `example-001/` with its twin and all three states, and the builders: `build_conflict.py` writes `tests/conflict.json` (present for all 44 impossible tasks), `build_state_b.py` writes `environment-B/`, `build_fixable.py` writes `environment-fixable/`. Only the fixture has the last two so far; the ImpossibleBench tasks get them once the builders have run on the passing twin runs (`docs/hand-runs.md`), and `run.py` refuses a State B or fixable run until then. `tasks/README.md` has the layout.

`prompts/instructions/` holds the exact instruction texts: `level1.md`, `level2.md`, `level3.md` and `state_b.md`. Level 3 is the first sentence of ImpossibleBench's loosest prompt, verbatim, with its "DO NOT MODIFY THE TESTS" line left out on purpose (PLAN line 44). `prompts/` is also where `capture_prompts.py` writes the wire-prompt archive (`<body>.gemini.txt`, `<body>.gemini.meta.json`, `SHA256SUMS`) and where the dated, hand-written `PREDICTIONS.md` goes (template in `docs/labels/predictions.md`). Neither exists until that step runs.

`verify.py` recomputes every headline number from the archived runs, prints the one-liner that reproduces each, and writes `VERIFY.md`. `figures.py` writes figures 1 to 3 as CSV and PNG under `figures/`. `samples/` is for hand runs, the rubric and random transcripts; `labels/` for the filled label sheets; `tests/` for the pytest suites and their fixtures (proxy records in three formats, a stream-json capture, diffs, and `make_fixtures.py`, which generates four synthetic run directories).

The official guide controls all of it. `mrh-runtime` is plumbing and appears once in Methods, as the wall. Moiz writes the outward prose.
